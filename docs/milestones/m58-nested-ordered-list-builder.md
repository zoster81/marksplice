# Milestone M58 — Nested Ordered-List Construction

Status: green — canonical homogeneous nested ordered-list construction with marker-width-aware indentation.

## Goal

Apply the M57 structural-depth model to ordered lists while preserving GFM indentation semantics across variable decimal marker widths.

M58 adds:

```go
func (b *DocumentBuilder) AppendNestedOrderedList(items ...ListItemInput) error
```

The `ListItemInput` contract is shared with M57.

## Canonical numbering and indentation

Every list container starts numbering at 1 and increments only among siblings in that container. Returning from descendants resumes the parent container's next ordinal. A newly entered child container resets to 1.

Child indentation is the generated parent content column, not a fixed three spaces. This matters once an ordinal grows from one to two digits. For example:

```text
9. item 9
10. item 10
    1. child of ten
11. item 11
```

The child under `10.` is indented four spaces because the parent content begins four columns after the physical line start.

## Shared implementation

M58 reuses the M57 iterative container-frame writer. Each depth frame records:

- physical container anchor;
- canonical indentation for that container;
- next ordered ordinal.

The writer keeps only O(depth) transient state and shares the same expectation/proof model with flat M45/M46 lists and task-list families.

## Parser/model proof

Every generated ordered item must reproduce exact marker/content/physical-line ranges plus:

- ordered semantics and `.` delimiter;
- correct semantic container anchor;
- expected parent anchor;
- direct child count;
- complete subtree boundary.

Because the source mapper derives the actual decimal marker start and Goldmark resolves parent/container semantics, acceptance does not depend on the writer merely having emitted plausible whitespace.

## Compatibility

M46 `AppendOrderedList` remains unchanged. Its internal items all have depth zero and now pass through the generalized list writer, preserving the historical canonical `1.`, `2.`, ... output.

No public parsed list type, `NodeID`, mutation API, or existing kind ordinal changes.

## Complexity

Writing is O(n) in generated bytes with O(d) transient depth frames. Decimal conversion is proportional to marker width. No ancestor-rescan loop is introduced.

## Devil's advocate review

### Risk: fixed child indentation fails after `9.`

Mitigation: the child indent is derived from the exact generated parent content column. The focused M58 test places a child under item 10 and requires four-space indentation.

### Risk: numbering continues globally inside nested containers

Mitigation: each depth/container frame owns its own `nextOrdinal`, which resets when a new child container is entered and resumes only for siblings in the same container.

### Risk: returning from a nested container loses the outer ordinal

Mitigation: truncating deeper frames preserves the shallower frame, so the next root sibling continues at the correct outer number.

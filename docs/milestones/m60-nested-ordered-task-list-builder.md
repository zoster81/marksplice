# Milestone M60 — Nested Ordered Task-List Construction

Status: green — nested ordered task-list construction combining M58 hierarchy/numbering with M48 task proof.

## Goal

Complete the first homogeneous nested-list construction family by combining ordered container-local numbering and marker-width-aware indentation with exact GFM task-marker/state validation.

M60 adds:

```go
func (b *DocumentBuilder) AppendNestedOrderedTaskList(items ...TaskListItemInput) error
```

`TaskListItemInput` is introduced by M59 and shares the same structural `Depth` contract as `ListItemInput`.

## Canonical source

Each ordered list container starts at 1 and increments only among siblings in that container. Task markers use canonical `[ ]` and lowercase `[x]`.

Example:

```text
1. [ ] parent
   1. [x] child
   2. [ ] sibling
2. [x] tail
```

Nested indentation is derived from the generated parent content column exactly as in M58; task syntax does not introduce a second indentation rule.

## Shared architecture

M60 adds no new internal construction kind, parser kind, source mapper, or persistent model. `AppendNestedOrderedTaskList` converts public inputs into the existing private list-item construction representation with task metadata, then reuses:

- M57/M58 depth validation and iterative per-container writer;
- M58 container-local ordinal state;
- M47/M48 exact task marker/state expectations;
- M22–M33 parsed list hierarchy/subtree proof.

This keeps the implementation converged rather than maintaining four separate flat/nested/task list writers.

## Compatibility and complexity

The historical `AppendOrderedTaskList` API and `TaskListItem` shape are unchanged. Existing flat ordered task-list output is preserved.

Writing remains O(n) in generated bytes with O(d) transient depth state. Task proof adds constant metadata per requested item. No recursive traversal or persistent construction tree is introduced.

## Devil's advocate review

### Risk: task syntax shifts the parent's effective child indentation

Mitigation: child indentation is based on the list item's generated content column before the task marker, matching the list container semantics already proven by Goldmark and the existing source mapper.

### Risk: nested ordered numbering leaks between containers

Mitigation: ordinals remain frame-local; each new child container starts at 1 and the outer frame survives descendant traversal so later root siblings resume correctly.

### Risk: list and task proofs can disagree silently

Mitigation: construction acceptance requires both the exact list-item expectation and the exact `KindTask` marker/state expectation for every task item.
